# v0.3.4 — Anthropic prompt-cache visibility + stable cwd + (opt-in) persistent claude subprocess

Shipped: 2026-05-17.
Branch: `main`.
Test totals at v0.3.4 close: **129 / 129 passing across the workspace**
(kimetsu-agent 79, kimetsu-brain 23, kimetsu-chat 21, kimetsu-cli 2,
kimetsu-core 0, kimetsu-harbor-rs 4).

## Motivation

After v0.3.3 the chat REPL was usable end-to-end, but cost-per-turn was
noticeably worse than running bare `claude -p` for an equivalent task.
A trace of one chat turn against the kimetsu codebase showed:

```
cache_creation_input_tokens: 6929
cache_read_input_tokens:    16540
```

So the Anthropic prompt-cache **was** being used, but most of the cache
work was happening **once per session** — kimetsu was paying full input
freight on the system prompt every model turn instead of letting the
cache amortize across turns.

Three structural causes were on the suspect list:

1. **No visibility.** `TokenUsage` only carried `input_tokens` +
   `output_tokens` + `cost_usd`. We literally couldn't tell whether
   cache_creation or cache_read was dominating turn-over-turn.
2. **Per-call tempdir.** Every `complete()` call created a fresh
   `$TEMP/kimetsu-claude-code-<run_id>/` and pointed `claude` at it as
   the working directory. Anthropic's prompt-cache keys include
   cwd-derived state — a new cwd every call meant a guaranteed cache
   miss on the system prompt every time.
3. **Per-call subprocess.** Every `complete()` call spawned a brand-new
   `claude` Node process. Even with stable cwd, two different
   subprocesses don't share session state, so the cache layer that's
   tied to "the same agent talking to itself" can never land.

v0.3.4 attacks all three in two commits.

## Part A — surface cache stats

### Wire-level

`TokenUsage` (in `kimetsu-agent::model`) gains two `u32` fields:

```rust
pub struct TokenUsage {
    pub input_tokens: u32,
    pub output_tokens: u32,
    pub cost_usd: f32,
    #[serde(default)] pub cache_creation_input_tokens: u32,
    #[serde(default)] pub cache_read_input_tokens: u32,
}
```

`#[serde(default)]` keeps existing on-disk traces parseable — older
runs without the fields deserialize to 0.

Both providers were updated to forward the new fields:

* **claude_code provider** — `ClaudeCodeUsage` (the stream-json `result`
  event) gains optional `cache_creation_input_tokens` and
  `cache_read_input_tokens`. `parse_claude_code_output` carries them
  into the `ModelResponse.usage`.
* **anthropic provider** — `AnthropicUsage` and its `From<AnthropicUsage>
  for TokenUsage` do the same, so callers using the anthropic API
  directly get the same visibility.

### Bug found during plumbing: multi-turn under-billing

While extending `run_model_agent` (in `kimetsu-agent::harbor`) to surface
cache stats, I noticed the loop variable was `last_usage`, **overwritten**
per turn:

```rust
let response = provider.complete(request)?;
last_usage = response.usage;
```

That means: a chat message that takes 5 model turns to resolve only
reports the **last** turn's cost to `cost.record_turn(...)`. Multi-turn
agent loops were under-billing the budget by however much was burned in
turns 1..N-1.

Renamed to `total_usage` and switched to saturating-add across all
counters (input_tokens, output_tokens, cost_usd, cache_creation,
cache_read). `cost.record_turn(report.usage.cost_usd)` now accurately
captures the full chat message's spend.

The same fix landed in `agent_loop.rs` (the pipeline path) for symmetry.

### Chat REPL surfacing

`run_repl` in `kimetsu-chat` prints a per-turn line whenever either cache
counter is non-zero:

```
[turn] cost=$0.0432  total=$0.0432/$10.00  turns=3  tool_calls=2
[cache] input=2340 output=410 cache_write=1820 cache_read=11200
```

`cache_write` dominating `cache_read` = the cache isn't landing.
`cache_read` growing turn-over-turn = ✅ v0.3.4e (when enabled) is
working.

## Part B — stable tempdir per `ClaudeCodeProvider`

`TempCommandDir` moved off `complete()`'s stack and onto a struct field:

```rust
pub struct ClaudeCodeProvider {
    // ...
    work_dir: Arc<TempCommandDir>,
}
```

Constructed once in `from_config_with_key`; lives for the provider's
lifetime. `complete()` reuses `&self.work_dir` and re-creates the inner
`config/` subdir defensively (cheap no-op when it's already there).

The `Arc` wrapper is forward-compat: if anyone reintroduces `Clone` on
`ClaudeCodeProvider`, the tempdir will be ref-counted instead of
double-dropped. Today's tree still wouldn't clone it — see Part E for
why.

## Part E — persistent claude subprocess (opt-in)

### What it does

When `KIMETSU_CLAUDE_PERSISTENT=1` (also accepts `true` / `yes`,
case-insensitive), `ClaudeCodeProvider` keeps one long-lived
`claude -p --input-format stream-json --output-format stream-json
--verbose --system-prompt <prompt>` subprocess alive across
`complete()` calls. Each call writes one newline-delimited `user`
event to the child's stdin and reads stdout events through a drainer
thread until a matching `result` event arrives.

Wire shape of the `user` event:

```json
{"type":"user","message":{"role":"user","content":"<prompt text>"}}
```

### Design

```text
ClaudeCodeProvider {
    api_key, model, timeout, work_dir,
    session: Option<PersistentClaudeSession>,
    persistent_enabled: bool,
}

PersistentClaudeSession {
    child:               Child,                                // long-lived
    stdin:               ChildStdin,                           // per-call writes
    stdout_rx:           Receiver<Result<Value, String>>,      // drainer→main
    _drainer:            JoinHandle<()>,                       // EOF-when-child-dies
    session_fingerprint: u64,                                  // hash(system_prompt, model)
}
```

* **Spawn discipline**: `session_fingerprint = hash(system_prompt,
  model)`. When the fingerprint changes (e.g. pipeline switches stages,
  model gets swapped), the session is dropped and respawned with the
  new system prompt. The `"::"` separator in the hash prevents naive
  string-concat collisions (covered by a regression test).
* **Idle timeout**: same `self.timeout` the one-shot path uses for
  `run_with_timeout_stdin`. If no events arrive on stdout for
  `timeout` seconds the session is killed and the call surfaces an
  Err.
* **Hard ceiling**: `3 * timeout`. Matches the one-shot contract.
* **Drop**: kills the child; the drainer thread sees EOF on stdout
  and exits naturally. Same thread-leak trade-off MP-4 made for
  one-shot (preferable to deadlocking on grandchild pipes).
* **Failure recovery**: any error inside `complete_persistent()`
  surfaces back up to `complete()`, which drops the session and falls
  through to the one-shot path. The user-facing call still succeeds —
  it just pays the spawn tax that turn. The next call respawns the
  persistent session cleanly.

### Refactor shared with Part A

`parse_claude_code_output()` was split into:

* **`parse_claude_code_output(stdout: &[u8])`** — the existing
  one-shot path. Walks all stream-json lines, picks the last `result`,
  hands it off.
* **`claude_code_json_to_response(response: ClaudeCodeJson)`** — the
  conversion (cache fields included). Shared between the one-shot
  path and the persistent path (which gets `ClaudeCodeJson` directly
  from the drainer thread's parsed `result` event).

### Why opt-in

The claude CLI docs say `--input-format stream-json` is "realtime
streaming input" and `--replay-user-messages` only makes sense in a
multi-event session, so we believe the CLI keeps reading stdin past
the first `result` event. But until a live run confirms that
`cache_read_input_tokens` actually grows turn-over-turn (which is
what v0.3.4a's `[cache]` line was designed to expose), the persistent
path stays opt-in. If the live validation confirms the design, v0.3.4f
flips the default to ON and drops the env gate. If the subprocess
exits after the first result event, we'll fall back to the
`--continue` + `--session-id` resume strategy.

## What this doesn't do (deferred)

* **Validation under load.** v0.3.4 ships the structure; v0.3.4f does
  the live-run validation that confirms `cache_read` grows. Until
  then `KIMETSU_CLAUDE_PERSISTENT=1` is a "try at your own
  observation" flag.
* **Streaming partial responses.** The drainer thread sees `assistant`
  delta events but throws them away — the chat REPL still blocks per
  turn. v0.3.5+.
* **Session resume from disk.** `claude --continue` + `--session-id
  <uuid>` would let us survive provider drops across `kimetsu chat`
  invocations. Deferred until we have the basic in-process persistent
  path validated.
* **Per-tool cost breakdown.** The agent loop accumulates total
  TokenUsage but doesn't attribute cost to specific tool calls.
  v0.3.5+ if/when users ask for it.

  output gains cache columns for free.
