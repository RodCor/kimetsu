# Kimetsu v0.2 Plan â€” Human-Curated Memory + Terminal-Bench

**One-line goal**: Iterate on stability and on the brain's marginal contribution
until the harness is **strictly better than no-brain on a public benchmark
(Terminal-Bench)**, with memory generation kept but the accept decision moved
to the human.

This document replaces auto-acceptance with a curated-pool middle ground and
pivots evaluation from the in-repo fixture bench to Terminal-Bench 2.0. The
v0.1 falsifiable claim (brain â‰¥ MVP threshold) has already passed; v0.2 raises
the bar to "brain + curated memories â‰¥ no-brain on Terminal-Bench."

## Why this shape

The MP-4 verdict (`MP-4-VERDICT.md`) showed three things at once:

1. The broker is unambiguously load-bearing (cold = 88% vs off = 0%).
2. Hand-curated memories take us to 100% with the cleanest plans (`brain_on_warm`).
3. Auto-accepted memories tie on success but cost 50% more â€” they admitted
   misleading entries the model proposed about itself.

The middle ground keeps the *proposal generation* (cheap, runs as a stage,
captures genuine patterns the agent noticed) and removes the *auto-accept
loop* (expensive in failure modes, no reliable quality signal at v0.1 sample
sizes). The user becomes the quality gate.

## Falsifiable goal for v0.2

Run Terminal-Bench 2.0 in three modes:

- **bare**: Claude Code, no Kimetsu wrapper
- **kimetsu-no-brain**: Kimetsu pipeline, `--no-broker` (broker disabled, no
  memory)
- **kimetsu-brain**: Kimetsu pipeline with broker + the curated memory pool
  built up by the user during dev

**v0.2 ships when:**

1. `kimetsu-brain` â‰¥ `kimetsu-no-brain` on Terminal-Bench accuracy AND
2. `kimetsu-no-brain` is within 5 pp of `bare` (no regression from the
   wrapper overhead) AND
3. Three consecutive Terminal-Bench runs over a 1-week window stay within
   Â±5 pp of each other (stability).

The bench shipped in v0.1 keeps running for unit-level signal on the broker
and pipeline; Terminal-Bench is the new top-line metric.

## Architecture pivot â€” Memory Proposal Review (MP-5)

Current MP-3 flow (auto-accept):

```
MemoryProposal stage â†’ memory.proposed â†’ auto_accept_policy_allows(proposal, shadow_pool)
                                       â†“
                                  accept_proposal() â†’ memory.accepted â†’ broker
```

v0.2 flow (human-curated):

```
MemoryProposal stage â†’ memory.proposed â†’ memory_proposals.status = "pending"
                                       â†“
              kimetsu brain proposal review (interactive CLI)
                                       â†“
                       user picks: accept | reject | edit | skip
                                       â†“
                            memory.accepted (if user accepts)
```

The `auto_accept_policy_allows` path stays in code but only fires when the
user explicitly passes `--auto` to `kimetsu brain proposal review`. It is
**off by default** and **off in the v0.2 Terminal-Bench runs**. The auto path
becomes a debugging tool, not a documented user flow.

## Phases

### MP-5: Human-curated memory queue (the "middle ground")

**Storage**: existing `memory_proposals` table already has the `status`
column. Add nothing schema-wise. The proposal flow already writes status =
"pending" via MP-3.

**CLI surface**:

```
# List pending proposals from the most recent runs.
kimetsu brain proposal list --status pending

# Interactive review session. Steps through each pending proposal,
# shows: rationale, normalized_text, source_event_ids, similar
# existing memories (jaccard preview from MP-4c), and prompts for:
#   [a] accept, [r] reject, [e] edit text/scope/kind, [s] skip,
#   [q] quit.
# Persists via existing accept_proposal / reject_proposal.
kimetsu brain proposal review [--limit N] [--scope SCOPE]

# Non-interactive batch accept for power users who trust a specific
# run's proposals.
kimetsu brain proposal review --run-id <id> --accept-all
kimetsu brain proposal review --run-id <id> --reject-all --reason "noise"

# Explicit opt-in to the old auto-accept policy (off in v0.2 default).
kimetsu brain proposal review --auto
```

**Acceptance criteria**:

- `kimetsu brain proposal review` runs in a TTY and works with `rustyline`
  or a hand-rolled stdin reader (no new heavy deps).
- The auto-accept code path stays callable for benchmarking the v0.1 vs v0.2
  delta but is not the default.
- The `kimetsu bench` runner gains a new mode `brain_on_curated_warm` that
  loads only memories explicitly accepted via the review flow (use the
  `provenance_snapshot_json.source == "review"` field).

**Why this works**: the per-task evidence in the MP-4 verdict showed memories
helped on rust_two_file_bug and hurt on rust_function_renamed. A human
reading the proposals would have rejected the rust_function_renamed entries
(too task-specific, didn't generalize). Curated memory captures the win
without the false-positive cost.

### MP-6: "Best memories" surfacing (the boosted retrieval path)

Once the curated pool exists, the broker should prefer memories that have
proven their value across runs. Reuse the MP-4a usefulness data:

- `kimetsu brain memory top [--limit 20] [--scope ...]` â€” list memories
  sorted by `usefulness_score / max(use_count, 1)` (the same ratio MP-4c
  uses) plus a small-sample threshold.
- Broker scoring already biases by usefulness from MP-4b; the change here is
  surfacing the top entries in CLI so the user can see what's actually
  pulling weight and prune the rest.
- Add `kimetsu brain memory prune [--min-uses N] [--max-ratio R]` for
  one-shot cleanup. Wraps existing `invalidate_memory` for entries below the
  threshold.

**Why this works**: curated proposals + usefulness data + prune-the-loser
loop gives us a steady-state where the brain only retrieves memories that
have demonstrably helped. This is the "only the best ones are suggested"
piece of the v0.2 brief.

### MP-7: Terminal-Bench harness integration

Harbor (Terminal-Bench's runner) is Python-based and expects an agent that
implements `harbor.agents.base.BaseAgent` with an async `run(instruction,
environment, context)` method. The agent is invoked inside Harbor's
Docker-managed environment and talks to the workspace via
`environment.exec(cmd)`.

Two options for plumbing Rust â†’ Harbor:

| option | description | tradeoff |
|--------|-------------|----------|
| **A. External agent** with Python wrapper | Thin Python class that calls `kimetsu.exe` as a subprocess. Kimetsu writes JSON-RPC tool calls to stdout; wrapper translates to `environment.exec()` and replies on stdin. | Most isolation, slowest startup. |
| **B. Installed agent** in Harbor's Docker image | Kimetsu binary baked into a Harbor docker image; Harbor invokes it headless inside the container. | Faster, but couples kimetsu builds to Harbor's image definitions. |

**Pick A for v0.2**: less coupling, easier to swap models, and keeps the
kimetsu binary as the single source of truth. The Python wrapper is
~80 lines and lives in `kimetsu_harbor/kimetsu_agent.py`.

**New kimetsu binary mode**:

```
kimetsu agent --harbor-mode --task "<instruction>"
```

In harbor mode the agent's tool layer is replaced: instead of `Command::new`
running locally, every tool call is serialized to a JSON-RPC line on stdout
(`{"jsonrpc":"2.0","method":"tool.exec","params":{...},"id":N}`) and the
result is read from stdin. This is a small ToolRuntime refactor â€” the
existing `RuntimeContext` already gates every tool execution through a
single dispatcher.

**Python adapter** (`kimetsu_harbor/kimetsu_agent.py`):

```python
import asyncio, json, os
from harbor.agents.base import BaseAgent

class KimetsuAgent(BaseAgent):
    @staticmethod
    def name() -> str: return "kimetsu"
    def version(self) -> str: return "0.2.0"

    async def setup(self, environment):
        # binary is pre-built into the Harbor image; nothing to install
        pass

    async def run(self, instruction, environment, context):
        proc = await asyncio.create_subprocess_exec(
            "/usr/local/bin/kimetsu", "agent", "--harbor-mode",
            "--task", instruction,
            stdin=asyncio.subprocess.PIPE,
            stdout=asyncio.subprocess.PIPE,
        )
        async for line in proc.stdout:
            msg = json.loads(line)
            if msg.get("method") == "tool.exec":
                result = await environment.exec(msg["params"]["command"])
                reply = {"jsonrpc":"2.0","id":msg["id"],"result":result}
                proc.stdin.write((json.dumps(reply)+"\n").encode())
                await proc.stdin.drain()
            elif msg.get("method") == "agent.done":
                context["final_summary"] = msg["params"]["summary"]
                break
        await proc.wait()
```

**Registration** is a single CLI flag at run time:

```
harbor run -d terminal-bench/terminal-bench-2 \
  --agent-import-path kimetsu_harbor.kimetsu_agent:KimetsuAgent \
  -n 32
```

**Acceptance criteria**:

- `kimetsu agent --harbor-mode --task "echo hello"` runs cleanly end-to-end
  with the Python wrapper proxying through a stub `environment.exec`.
- `harbor run -d terminal-bench/terminal-bench-2 -a oracle -n 4` works (the
  oracle smoke test confirms Harbor + Docker is set up correctly).
- The kimetsu adapter completes â‰¥1 real Terminal-Bench task end-to-end.

### MP-8: V0.2 baseline measurement and stability gate

Once MP-5 (curated memory), MP-6 (best-of), and MP-7 (Harbor adapter) are
in, run the Terminal-Bench gauntlet:

1. **Curate the memory pool**: run the v0.1 fixture bench in
   `brain_on_auto_warm` mode, then `kimetsu brain proposal review` over
   the proposals it produced. This builds a memory pool from real runs,
   not a hand-typed list.
2. **Three Terminal-Bench runs**:
   - `bare`: `harbor run -d terminal-bench/terminal-bench-2 -a claude-code -n 32`
   - `kimetsu-no-brain`: kimetsu adapter with `KIMETSU_DISABLE_BROKER=1`
   - `kimetsu-brain`: kimetsu adapter with broker + curated memories
3. **Stability check**: repeat each mode 3 times over 1 week. Variance
   within Â±5 pp = stable. Variance >5 pp â†’ drill into the offending task
   class, repeat.
4. **Ship gate**: `kimetsu-brain` â‰¥ `kimetsu-no-brain` â‰¥ `bare - 5pp` AND
   all three runs stable.

If `kimetsu-brain` underperforms `kimetsu-no-brain`, MP-4's kill criterion
extends to v0.2 and personal memory becomes a v0.3 problem. The harness
itself still ships if it meets the no-regression bar against `bare`.

## What stays from v0.1

- The whole broker + capsule scoring stack (load-bearing in MP-4 verdict).
- `prior_run` capsules (the largest single source of uplift after the
  broker itself).
- `kimetsu brain memory add` for manual curation. Power-users still get
  the warm-curated path.
- The fixture bench (5 modes incl. ablation). Faster signal during dev
  than the full Terminal-Bench run.
- Tool runtime, agent loop, retry-with-fingerprint, verification stage.

## Out of scope for v0.2
