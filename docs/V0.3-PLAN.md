# Kimetsu v0.3 Plan

**One-line**: kimetsu graduates from Terminal-Bench harness to a real
interactive coding agent product. The agent core stays unchanged
(20-tool surface, brain integration, MP-18 iterative verify); we add a
new transport (`kimetsu chat`) and split harbor/Terminal-Bench code
out of the agent core into its own crate so chat can ship without
dragging benchmark machinery along.

## The two big moves

### 1. New `kimetsu chat` transport

A standalone interactive REPL that turns the kimetsu agent runtime —
already validated against Terminal-Bench across 18 development phases
— into a real product surface. The user types messages in their
terminal, kimetsu drives the model + tools against their actual
filesystem (not a Harbor container), MP-18's iterative goal verify
catches "I think I'm done" → "no you're not" failure modes, and the
brain accumulates `failure_pattern` memories across sessions.

Slash commands:
- `/help` — list commands
- `/quit` — exit
- `/cost` — running cost vs budget
- `/goal [<text>]` — set or recall the session goal (drives MP-18 verify)
- `/strict on|off` — toggle MP-18 strict mode (require record_deviation)
- `/memory <args>` — passthrough to kimetsu-brain CLI semantics

### 2. Crate split: harbor out of agent

Today `kimetsu-agent/src/harbor.rs` is 3000+ LOC of mixed concerns:
the protocol-agnostic agent loop alongside Terminal-Bench-specific
JSON-RPC machinery. v0.3 introduces `kimetsu-harbor-rs` as a separate
crate so `kimetsu-chat` (and any future transport — HTTP, MCP, VS
Code extension) doesn't depend on benchmark code.

For v0.3.0 the harbor split is a **two-phase migration**:
- **Phase 1 (this scaffold, shipped now)**: new `kimetsu-harbor-rs`
  crate exists as a re-export shell over `kimetsu_agent::harbor`. The
  dependency direction is correct from day one — `kimetsu-cli` depends
  on `kimetsu-harbor-rs` for harbor mode, on `kimetsu-chat` for chat
  mode, on neither for `brain`/`init`/`config`. Nothing physically
  moves yet; that comes in Phase 2.
- **Phase 2 (v0.3.1)**: physically migrate HarborSession + JSON-RPC
  types from `kimetsu-agent/src/harbor.rs` into `kimetsu-harbor-rs/`,
  leaving `kimetsu-agent` with only the protocol-agnostic runtime.

This phasing keeps every prior gauntlet result reproducible against
v0.3.0 — nothing about MP-18 semantics changes, and HEAD compiles to
the same binary modulo new subcommands.

## Workspace layout

```
crates/
  kimetsu-cli/           binary `kimetsu`. Subcommands:
                           agent --harbor-mode   → kimetsu-harbor-rs
                           chat                  → kimetsu-chat   (NEW)
                           brain ...             → kimetsu-brain
                           init / config / run / bench / runs / lock
  kimetsu-agent/         AGENT RUNTIME — protocol-agnostic core.
                         Continues to host harbor.rs in v0.3.0 (re-exported
                         by kimetsu-harbor-rs); Phase-2 will trim it down
                         to only the transport-agnostic pieces.
  kimetsu-harbor-rs/     NEW. Terminal-Bench transport adapter. Today:
                         re-export shell. v0.3.1: physical home of
                         HarborSession + JSON-RPC types + harbor entry
                         point.
  kimetsu-chat/          NEW. Interactive REPL transport. Slash commands,
                         cost meter, host-filesystem tool runtime. Has
                         ZERO dependency on kimetsu-harbor-rs.
  kimetsu-brain/         unchanged
  kimetsu-core/          unchanged
kimetsu_harbor/          unchanged (external Python adapter for Harbor)
```

## What ships in v0.3.0

Concrete deliverables landed in the first v0.3 commit:

1. **`kimetsu-harbor-rs` scaffold** — Cargo manifest + `src/lib.rs`
   exporting the harbor surface kimetsu-cli needs. Re-export only, no
   physical migration.
2. **`kimetsu-chat` skeleton with full API surface and tests**:
   - `ChatConfig` + `ChatError` + `run_repl(reader, writer, config)`
   - `SlashCommand::{Help, Quit, Cost, Goal, Strict, Memory}` parser
   - `CostMeter` with budget tracking + max-turn observation
   - 17 unit tests covering the REPL skeleton, slash commands, cost
     accounting, and brain-project validation
3. **`kimetsu chat` CLI subcommand**:
   - `--workspace`, `--project`, `--model`, `--max-cost-usd`, `--goal`,
     `--strict` flags
   - Routes through `kimetsu_chat::run_repl` over stdin/stdout
4. **Brain-project validation** on session start — surface errors up
   front instead of mid-session
5. **No regression**:
   - kimetsu-agent: 82/82 tests green (MP-18 + all prior phases)
   - kimetsu-brain: 23/23 tests green
   - kimetsu-chat: 17/17 tests green (new)
   - Total: **122/122 tests passing across the workspace**

## What's deferred to v0.3.1

The chat REPL is an **alpha scaffold** in v0.3.0 — the dependency
direction and CLI surface are real, but the model round-trip inside
`run_repl` is a placeholder echo. v0.3.1 wires it through:

- Construct `ClaudeCodeProvider` from `CLAUDE_CODE_OAUTH_TOKEN` env
- Construct host-side `ToolRuntime` (already exists; just call
  `ToolRuntime::new(workspace, run_id)`)
- Build a session-state-aware version of `run_model_agent` that
  speaks REPL semantics instead of JSON-RPC (the agent loop's tool
  dispatch + verify logic is fully reusable — only the I/O wrapper
  differs)
- Bridge `record_deviation` calls to `kimetsu-brain` proposals at
  session end (`kimetsu brain memory review --from-run <chat_session_id>`)
- Stream model output to stdout as events arrive (so users see
  partial responses, not block-of-text-after-30-seconds)
- Render tool calls + results inline (filename + diff + result summary)
- Implement the actual `/memory add` / `/memory list` semantics by
  delegating to `kimetsu-brain::project::add_memory` / `list_memories`

Phase-2 architectural migration (also v0.3.1):

- Move `HarborSession<R, W>`, `HarborShellExecutor<R, W>`,
  `HarborRequest` enum, `JsonRpcResponse` / `JsonRpcError`,
  `ToolExecParams` / `ToolExecResult` from `kimetsu-agent/src/harbor.rs`
  into `kimetsu-harbor-rs/src/session.rs`
- Move `run_stub_agent` + `run_multi_step_stub` (harbor-only stubs
  used by tests) into `kimetsu-harbor-rs/src/test_stubs.rs`
- Keep `run_model_agent` + tool registry + verify in `kimetsu-agent`
  but rename the file from `harbor.rs` to `agent.rs` or split into
  `agent_loop.rs` + `tools_registry.rs` + `verify.rs` + `prompts.rs`
- `kimetsu-harbor-rs::run_harbor_session(...)` becomes the canonical
  harbor entry point; `kimetsu-cli` calls it instead of reaching into
  `kimetsu_agent::harbor::*`

## Why scaffold-first instead of one big bang

- The MP-18 brain-only gauntlet is currently in flight. The Linux
  binary at `/mnt/e/Kimetsu/target/release/kimetsu` was compiled from
  HEAD at `ac20d9d`. Source edits in this commit don't affect the
  running gauntlet — but they DO affect the next rebuild. By keeping
  Phase-1 a pure re-export, the harbor binary path is bit-identical
  to MP-18's binary, so when the cron rebuilds nightly there's no
  drift in benchmark behavior to attribute.
- The new crates establish the dependency direction we want.
  `kimetsu-chat` depending on only `kimetsu-agent` (not
  `kimetsu-harbor-rs`) is enforced by Cargo. If anyone ever tries to
  shortcut by importing harbor types into chat, the compiler refuses.
- Tests cover the new surface area incrementally: 17 chat-side tests
  for slash commands, cost meter, REPL skeleton, brain validation
  ship in v0.3.0 even though the agent round-trip is deferred.
- Phase-2's physical migration is purely mechanical (move types, fix
  paths). Easier to land + review when the SCAFFOLD work has already
  validated the architecture.

## Concrete code review of the scaffold

To verify the architectural claim — chat doesn't depend on harbor —
the dependency graph after this commit:

```
kimetsu-cli  ─→ kimetsu-agent
              ─→ kimetsu-brain
              ─→ kimetsu-chat     ─→ kimetsu-agent
                                  ─→ kimetsu-brain
                                  ─→ kimetsu-core
              ─→ kimetsu-harbor-rs ─→ kimetsu-agent (re-export only)
                                   ─→ kimetsu-brain
                                   ─→ kimetsu-core
              ─→ kimetsu-core
```

`kimetsu-chat` and `kimetsu-harbor-rs` are SIBLINGS. Neither depends on
the other. The CLI is the only crate that pulls in both. Cargo would
reject any code in `kimetsu-chat` that tried to use harbor types
without an explicit dependency. The architecture is enforced.

## Carry-over from v0.2

Nothing about v0.2's invariants regresses:

- 20-tool surface intact, exposed by kimetsu-agent
- Brain memory pool, retrieval, MMR, dedup, usefulness-weighted —
  unchanged
- MP-18 record_deviation tool + iterative verify — unchanged
- Stability cron / harbor mode / kimetsu_harbor python adapter —
  unchanged paths
- The MP-18 gauntlet currently in flight is meaningful: its result
  reflects the v0.2 → v0.3 cut-over commit (ac20d9d). v0.3 scaffold
  doesn't perturb that measurement.
